Universal UI Reference Library and Design Principles Dossier
A reusable corpus of shipping interfaces, interaction patterns, implementation ranges, and critical design lessons
Research edition • 9 September 2026 • Companion index contains 33 filterable references
Purpose
This dossier answers a practical question: what does excellent interface design look like when it has to survive real data, real permissions, real latency, small windows, touch input, keyboard use, and irreversible actions? The references favor shipping products and official documentation. Marketing images are used only when they show a specific, plausible product state. Historical material is labeled rather than quietly presented as current.
Use the document to choose patterns and rules. Use the companion index to filter by platform, interaction, component, evidence strength, or currentness, and to revisit the original screen, video, or documentation.

A  Executive summary
Excellent UI concentrates visual and behavioral emphasis at the current decision. Merely competent UI often has consistent components but gives too many things equal weight. The strongest references in this corpus repeatedly do seven things.
1  They spend hierarchy, not decoration.  Raycast spends contrast on the query and selection; Linear spends it on priority and unread state; Stripe spends it on the order, fields, and final commitment. None needs a card around every section. [1][3][12]
2  They make interaction state local.  Notion anchors block actions to the block, Superhuman attaches a follow-up chooser to sending, and Google Photos keeps edit history beside the edited image. The control appears where its consequence is visible. [9][11][21]
3  They keep a stable spatial model.  VS Code overlays commands without replacing the editor, GitHub keeps the repository behind its palette, and Google Maps lets a sheet expand over persistent geography. Context survives transient work. [5][10][20]
4  They distinguish input modes.  Figma exposes keyboard focus in place, Things adds direct-manipulation gestures without removing tap paths, and iPadOS changes navigation presentation as width and pointer precision change. [8][16][29]
5  They show the real status of work.  GNOME uses determinate progress only when progress can be measured; Pixel Recorder shows elapsed time, live output, and unambiguous Pause and Stop; Live Activities carry meaningful background state outside the app. [14][22][30]
6  They reserve interruption for consequence.  GNOME names the file and destructive verb; Android’s system prompt offers a one-time permission; Stripe keeps the order visible through payment. Confirmation is proportional to risk. [13][28][12]
7  They treat restraint as active editing.  Bear, iA Writer, and Things remove chrome only after investing in measure, baseline, focus, hit areas, shortcuts, and state feedback. Minimalism without those details is merely missing UI. [17][19][15]
The practical standard
• One dominant task per surface; one obvious primary action per decision.
• Stable alignment rails across rows, forms, and panels.
• Contextual controls that appear through hover, focus, selection, gesture, or direct manipulation.
• Keyboard paths that mirror pointer paths and expose shortcuts while the user works.
• Real empty, loading, success, failure, permission, and recovery states—not decorative placeholders.
• Motion that explains origin, destination, continuity, or status and disappears under reduced motion.
• System conventions preserved where they buy trust, accessibility, or learned behavior.
B  Reference library by interaction category
B1  Contextual and transient UI
The best transient surfaces are small because the underlying context does most of the explanatory work. Raycast’s Action Panel binds commands to the selected object, keeps the primary action first, groups the rest, and aligns shortcuts to a right rail. Notion offers three context-sensitive paths into the same block model: hover handles for pointer users, slash insertion for keyboard flow, and a toolbar above the mobile keyboard. Superhuman’s reminder chooser appears at send time and offers presets before custom scheduling. Google Maps preserves the map beneath its planning sheet. [2][9][11][20]
• Popover: use for a reversible local choice anchored to a control or selected object.
• Compact inspector: use when values must remain visible while the user manipulates the object.
• Sheet: use when context should remain visible but the task needs more vertical room or several detents.
• Modal: use when proceeding elsewhere would create ambiguity or risk.
• Toast with undo: use for completed, low-risk, reversible actions.
• Inline confirmation: use when the action can be resolved in the same row without blocking unrelated work.
Do not let transient UI become a second application. If a popover gains deep navigation, a form with several validation states, or a long-lived draft, promote it to a panel or page. If dismissing would lose entered work, warn or preserve the draft.
B2  Command palettes and keyboard-first interfaces
Raycast is the strongest general-purpose reference because query, ranking, primary action, alternate actions, and shortcuts share one consistent shell. VS Code is stronger for mode-rich professional software: the palette, Quick Open, symbols, and settings use related behavior while retaining the editor. GitHub adds explicit repository scope and visible entity prefixes. Figma filters commands by canvas selection so a global surface remains context-aware. Things shows the opposite extreme: type-to-navigate without a visible launcher until input begins. [1][2][5][7][10][15]
Observed implementation envelope  Compact desktop command surfaces in this set commonly fit a 560–720 px-wide window, a 44–52 px query row, 36–44 px result rows, 16–20 px icons, 12–16 px horizontal row padding, and 6–10 visible results before scrolling. These are measured design ranges, not vendor specifications.
• Focus the query immediately and keep the active scope legible.
• Use one selected row with a flat fill; avoid a card around every result.
• Place icon, primary label, metadata, and shortcut on fixed rails.
• Keep Enter, arrows, Escape, and alternate-open behavior identical across modes.
• Show recent or frequent actions before an empty list.
• Flatten groups when filtering, but preserve enough metadata to disambiguate.
• Teach advanced grammar through the empty state and placeholder, not a separate manual.
Failure mode: a command palette with weak ranking turns recognition into recall. If users must know the exact feature name, the surface is a search box over the organization chart, not a useful command system.
B3  Typography-led interfaces
Bear, iA Writer, Craft, Things, and Linear show five different ways type can carry an interface. Bear uses a writing-first measure and syntax color. iA Writer uses focus attenuation and a stable reading column. Craft uses editorial spacing and restrained metadata within documents. Things uses friendly type and spatial grouping to keep tasks from feeling like database rows. Linear uses compact type, muted metadata, and exact baselines to make dense operational data calm. [3][15][17][18][19]
• Use 60–75 characters per line for sustained reading and writing.
• On compact desktop product surfaces, 13–15 px body text with 18–22 px line height is a sound starting range.
• Use 11–13 px labels only for genuinely secondary metadata, with strong contrast and short line length.
• Use weight and space before adding a container. A 16 px gap between groups often communicates more cleanly than a border.
• Keep authored content darker or more saturated than the editor chrome.
• Limit routine interface typography to three or four roles: body, secondary, label, and heading. Add display sizes only when content warrants them.
B4  Forms and settings
Stripe Checkout, Google Calendar, macOS System Settings, Raycast Settings, and GNOME illustrate a common rule: fields should read as a decision sequence, not a gallery of components. Stripe separates order from payment; Calendar keeps the day nearby; macOS aligns app names and permission toggles; GNOME keeps confirmation language specific. [12][13][23][31]
• Place labels above fields or in a stable leading column; do not rely on placeholder-only labels.
• Group fields by intent and consequence. Use 20–32 px between groups and 8–12 px between label, field, and help text.
• Keep a consistent trailing rail for toggles, values, and status.
• Use help text before risky choices and validation beside the affected field.
• Separate destructive account actions from ordinary preferences with space, heading, and consequence text—not a theatrical red card.
• Keep the commit action visible after validation errors and preserve all entered values.
B5  Navigation systems
Dia, Superhuman, Google Maps, Google Keep, iPadOS, and Google Chat cover persistent sidebars, multi-pane workspaces, sheet-based navigation, content grids, and adaptive tab/sidebar behavior. The shared quality is continuity: selection, route, and content remain recognizable while the presentation changes. [6][11][20][25][29][32]
• Use a sidebar when labels, nesting, and frequent switching matter.
• Use tabs for a small set of peer destinations, not an arbitrarily growing hierarchy.
• Use bottom navigation for three to five high-frequency mobile destinations.
• Use breadcrumbs when the path itself helps orientation or supports jumping upward.
• Use search-first navigation when the item set is large, users know names, and ranking can be good.
• At responsive breakpoints, change presentation without changing route identity or resetting work.
B6  Loading and progress
Loading treatment should respond to elapsed time and certainty. The thresholds below are implementation heuristics synthesized from platform guidance and the reference behavior; they are not universal constants. GNOME, Android progress guidance, Pixel Recorder, and Apple Live Activities provide the clearest models. [14][22][30][39]
Under 300 ms  Do not flash a spinner. Use immediate pressed feedback and complete the transition.
300 ms to 1 s  Preserve layout. Use an inline busy mark, content placeholder, or delayed spinner only if the user needs reassurance.
1 to 3 s  Show an indeterminate indicator with a concrete status phrase. Avoid blocking the whole screen unless the result is prerequisite.
3 to 10 s  Use determinate progress when the denominator is credible; otherwise show the active phase. Offer Cancel when safe.
Over 10 s  Support backgrounding, notification on completion, persistence across navigation, and a recoverable failure state. Show elapsed or estimated time only when it is trustworthy.
Skeletons are useful only when the final structure is stable. A shimmering fake layout that then jumps to different geometry creates two loading events. Reserve skeleton motion for the region still resolving, not the entire application.
B7  Confirmations and permissions
The most polished confirmation is often undo. Use a modal when the action is consequential, difficult to reverse, affects another person or account, or requires a clear consent boundary. GNOME’s Replace File dialog, Gmail’s unsubscribe confirmation, Android’s one-time permission, Calendar’s invitation effects, and Stripe’s final payment action show different levels of friction. [12][13][23][24][28]
• Low risk and reversible: perform, then offer Undo.
• Meaningful but local: inline confirmation or two-step control.
• Irreversible or remote: modal with named object and specific verb.
• Permission: explain the benefit in context, then invoke the genuine system prompt.
• Payment or send: keep amount, recipient, or audience visible at commitment.
• Failure: explain what succeeded, what did not, and whether retry duplicates work.
B8  Mobile interface references
The strongest mobile references do not scale down desktop layouts. Google Maps layers a draggable sheet over geography; Google Photos enters an immersive edit mode; Pixel Recorder uses the screen for current status and reachable transport controls; Calendar preserves temporal context around a compact form; Apple Journal separates source selection from publishing; Niagara turns edge motion into alphabetic navigation; Things lets users drag creation to an exact list position. [16][20][21][22][23][26][27]
B9  Desktop interface references
Desktop quality comes from precision, continuity, and alternate input paths. Raycast, VS Code, Figma, Linear, Dia, Bear, macOS Settings, and GNOME exploit hover, pointer precision, keyboard focus, multi-pane layouts, toolbars, context menus, and transient windows. Their density works because baselines and rails are stable and because secondary commands do not occupy permanent space. [1][3][5][6][8][13][17][31]
B10  Motion and micro-interactions
Things uses motion to explain insertion and reordering. Apple Live Activities morph between compact and expanded states while preserving essential values. Linear shows revisions in place rather than replacing the document. Notion uses insertion guides and object-local menus to connect cause and destination. These patterns move state, not decoration. [4][9][16][30]

D  Reusable visual rules
D1  Spacing system
Use a 4 px base with an 8 px default rhythm. Carbon’s published scale—2, 4, 8, 12, 16, 24, 32, 40, 48, 64, 80, 96, and 160 px—is a useful completeness check, but most products should expose fewer tokens. [34]
• 2–4 px: optical correction, icon/text tuning, hairline separation.
• 6–8 px: icon-to-label, tight inline metadata, compact control internals.
• 10–12 px: compact row vertical padding or control inset.
• 16 px: default mobile edge inset and common desktop panel padding.
• 20–24 px: form groups, panel sections, dialog interior.
• 32–48 px: separation between major page sections.
• 48–80 px: reading-canvas or marketing-scale whitespace, not routine application rows.
• Desktop outer padding: 16–24 px for dense utilities; 24–40 px for standard product pages; 48–64 px for focused reading canvases.
• Mobile horizontal padding: usually 16–20 pt/dp; maintain safe-area spacing independently.
• Do not use equal gaps everywhere. Smaller gaps bind label to value; larger gaps separate groups.
D2  Density and row geometry
• Compact desktop menu or result row: 32–40 px; use 36–44 px when subtitles or mixed icons appear.
• Standard desktop list row: 40–52 px; 52–64 px for two-line content.
• Touch list row: 48–60 dp/pt minimum in practice; preserve at least a 44 pt iOS or 48 dp Android hit area. [36][37]
• Command search field: 44–52 px tall; persistent app search can be 40–48 px desktop or 48–56 dp mobile.
• Desktop icon: 16–20 px; mobile icon: 20–24 dp/pt. Keep the hit target larger than the glyph.
• Avatar: 24–32 px compact desktop, 32–40 px standard lists, 40–48 dp touch-first identity rows.
• Use one density per region. A compact sidebar can sit beside a spacious reading canvas, but do not alternate row heights arbitrarily inside a list.
D3  Typography
Carbon’s productive type set starts at 14 px and its expressive set at 16 px. The reference corpus supports a similar split between dense tools and reading surfaces. [35]
• Desktop productive body: 13–15 px with 18–22 px line height.
• Mobile body: about 16–17 pt/sp with 21–24 pt/sp line height.
• Helper or metadata: 11–13 px desktop, 12–14 pt/sp mobile; never let secondary mean illegible.
• Compact section heading: body size or +1 px, medium or semibold, with additional space above.
• Page heading: 24–32 px desktop; 22–28 pt mobile. Use size jumps sparingly.
• Long-form measure: 60–75 characters. Form and setting text can run wider because it is scanned in chunks.
• Prefer sentence case. Use all caps only for very short, rare, highly structural labels.
• Tabular numbers for times, counters, and changing metrics prevent jitter.
D4  Surfaces, borders, radius, and elevation
• Default page background plus one raised surface is usually enough. Do not create a new surface for every group.
• Use 1 px low-contrast dividers where scanning needs a rail. Replace unnecessary dividers with 8–24 px of space.
• Choose two or three radii: 4–6 px for compact controls, 8–12 px for popovers and cards, 16–24 px for mobile sheets or large modals.
• Nested radii should look concentric: inner radius is approximately outer radius minus the inset.
• Use shadows to establish overlap, not to make every component look premium. A border plus subtle shadow often beats a large blur.
• Dim backgrounds only for true modality. Popovers normally need local elevation without a full-screen scrim.
D5  Interaction states
• Hover: modest fill or tint change; do not move geometry.
• Focus: visible 2 px outline or equivalent high-contrast treatment, outside the control when possible.
• Pressed: immediate tonal or scale feedback; return within roughly 70–120 ms.
• Selected: persistent fill, marker, or type treatment that survives pointer departure.
• Disabled: lower emphasis but retain legibility; explain unavailable consequential actions.
• Loading: preserve label and width where possible; a spinner should not erase the action’s meaning.
• Error: show local message and recovery action; do not rely on a red border alone.
• Success: confirm completion at the scale of the task; avoid celebratory animation for routine saves.
D6  Modal, popover, panel, or page decision
• Popover when the task is anchored, brief, reversible, and dismissible.
• Panel when the user must compare the transient task with persistent content.
• Modal when leaving the decision unresolved creates risk or ambiguity.
• Page when the task has deep navigation, long-lived state, extensive validation, or a shareable URL.
• Bottom sheet when mobile context should remain visible and the task benefits from drag, detents, or reachability. [38]
D7  Hierarchy heuristic
At any pause point, blur the screen mentally. The dominant mass should correspond to the next decision or the content being manipulated. If five colored cards, several equal headings, and multiple primary buttons survive the blur, the hierarchy is unresolved. Reduce channels in this order: decorative color, shadow, borders, containers, icon backgrounds, duplicated labels. Then strengthen the one primary element with position, size, or contrast.
E  Motion rules
Carbon provides a useful implementation baseline: 70 ms for button and toggle micro-interactions, 110 ms for fades, 150 ms for small expansion or short travel, 240 ms for expansion and toasts, 400 ms for large expansion or important notification, and 700 ms for background dimming. Carbon also recommends roughly 90–120 ms for common micro-interactions and longer duration for larger distance or size change. [33]
• Pressed and hover feedback: 70–120 ms.
• Small menu, tooltip, or local popover: 120–180 ms.
• Sheet, inspector, or medium panel: 180–280 ms.
• Large layout morph or full-screen navigation: 240–420 ms.
• Background scrim: may trail content and take 300–500 ms; avoid delaying interactivity.
• Use entrance easing for arriving elements, exit easing for elements leaving permanently, and standard easing when an element remains conceptually nearby.
• Productive standard curve: cubic-bezier(0.2, 0, 0.38, 0.9). Productive entrance: cubic-bezier(0, 0, 0.38, 0.9). Productive exit: cubic-bezier(0.2, 0, 1, 0.9). [33]
• Animate opacity and transform when possible. Animate height only when the changing boundary itself carries meaning.
• Preserve at least one continuous element across a large transition: title, selected object, image, route, or position.
• For list reordering, animate the moved row and use restrained fades for displaced content; avoid crossing paths that obscure identity.
• Success and failure should update the element that caused them. Do not launch unrelated confetti or full-screen animation for routine work.
• Reduced motion: remove travel, parallax, spring overshoot, and repeated shimmer; use fades, instant state changes, and static status text.
E1  Motion audit
• What state changed?
• Which object caused the change?
• Where did the new element come from and where will it go?
• Does motion preserve identity or merely attract attention?
• Can the task be understood on the first and last frame?
• Does reduced motion preserve the same information and controls?
• Does the transition remain smooth under slow devices and interrupted input?
F  Desktop-specific lessons
• Exploit hover for preview and discovery, but reveal the same action on focus and in context menus.
• Keep keyboard focus visible across sidebars, canvas, toolbars, lists, and transient windows.
• Use menu bars and context menus for breadth; use toolbars for frequent visible actions; use command palettes for search and recall.
• Allow pointer-dense visual controls to remain 28–36 px tall while maintaining accessible focus and hit behavior.
• Use multi-pane layouts when simultaneous comparison matters. Preserve selection and scroll as panes collapse.
• Treat window resize as a first-class state. Test narrow, standard, wide, maximized, and multi-window arrangements.
• Place inspectors beside the object when persistent adjustment matters; use popovers for brief local choices.
• Restore window, route, selection, and unfinished work when reopening a professional tool.
• Do not apply mobile-sized whitespace to every desktop row. Density is a productivity feature when alignment and contrast are precise.
• Honor platform-native shortcuts, menu placement, text selection, drag-and-drop, and permission flows.
G  Mobile-specific lessons
• Keep touch targets at least 44 pt on Apple platforms and 48 dp on Android, even when glyphs are smaller. [36][37]
• Put high-frequency actions in reachable lower regions, but keep destructive or rare actions separated.
• Use sheets to preserve context, not as a default container. Define collapsed, intermediate, expanded, dismissed, keyboard-open, and rotated states.
• Provide a visible alternative for every gesture. Teach unusual gestures at the moment they become useful.
• Use edge and system inset awareness for navigation, drag handles, floating buttons, and maps.
• Preserve content position when the keyboard opens; do not hide the active field or commit action.
• Bottom navigation suits three to five durable destinations. More destinations need hierarchy, search, or an overflow strategy.
• Use haptics for a semantic boundary such as selection, commit, threshold, or error, synchronized with visible feedback. Do not use haptics as decoration.
• Pull-to-refresh is appropriate when the list has a meaningful remote refresh. Show the updated state and avoid erasing locally cached content.
• Test long labels, dynamic type, screen readers, reduced motion, dark mode, poor networks, denial, and one-handed reach.
H  Google-esque design lessons
High-quality Google interfaces are polished because several systems reinforce each other: readable type, familiar icons, strong baseline alignment, content-preserving surfaces, restrained brand color, and adaptive components. Calling this Material 3 is incomplete. Google Maps works because map, sheet, route, and controls form one spatial model. Calendar works because the form follows the sequence of scheduling decisions. Photos works because the artifact dominates during editing. Recorder works because status is redundant and honest. [20][21][22][23]
What is genuinely good
• Search is treated as navigation infrastructure rather than a decorative header field.
• Primary information often sits on a neutral or content-colored plane; brand colors mark action, identity, or state.
• Iconography uses consistent stroke, optical size, and familiar placement.
• Surface hierarchy is shallow: background, working surface, transient surface, modal scrim.
• Transitions preserve the source object or spatial context, especially in sheets and focused editors.
• Components adapt by width and input model rather than merely scaling.
• Forms use plain rows and grouping; settings use stable leading labels and trailing values.
• Contextual actions appear beside the selected content and recede afterward.
What becomes generic when copied mechanically
• Large rounded search bars on screens where search is not the primary route.
• Pastel surface containers around every content group.
• Filled tonal buttons used at several equal levels.
• Multicolor icons with no semantic relationship to the content.
• Floating action buttons added because the kit provides one, not because creation deserves constant reach.
• Bottom sheets used as general-purpose pages with too much hierarchy.
• Material defaults shipped without density, type, color, and motion decisions specific to the product.
How to capture the quality without cloning Google
• Adopt the behavioral discipline: context preservation, honest state, strong rails, narrow surface hierarchy, and adaptive components.
• Choose a product-specific type voice, radius set, and accent strategy.
• Use your domain’s visual material—maps, code, documents, media, data—as the dominant texture.
• Keep one family of icons and tune optical size rather than surrounding each icon with a colored chip.
• Use motion to connect state and location, not to imitate a branded easing demo.
• Prototype the ugly states early: denial, error, empty, slow, narrow, keyboard-open, and offline.
I  Vibecoded UI anti-pattern checklist
Generated interfaces usually look amateur because they assemble individually fashionable components without an information model. The following checklist compares common symptoms with the stronger references in this corpus.
Card inflation
Symptom  Every section sits in a rounded rectangle with shadow.
Strong comparison  Linear and Bear use spacing, type, and rows until a real surface boundary is needed.
Repair  Remove containers from related content. Add back only those that establish overlap, selection, or independent behavior.
Pill inflation
Symptom  Tabs, filters, statuses, labels, and buttons all become capsules.
Strong comparison  Raycast and VS Code reserve compact chips for scope or shortcuts; most actions remain plain rows.
Repair  Limit pills to a specific semantic class. Use text, rows, or checkmarks elsewhere.
Arbitrary gradient
Symptom  A purple-blue wash attempts to supply identity.
Strong comparison  Stripe and Google use neutral structure and sparse semantic color.
Repair  Start in grayscale. Add one accent role and one status palette only after hierarchy works.
Radius drift
Symptom  Inputs, cards, dialogs, and buttons each have unrelated curvature.
Strong comparison  GNOME and Apple system surfaces use a small, coherent radius family.
Repair  Choose two or three radii and verify nested concentric geometry.
Shadow roulette
Symptom  Every surface casts a different blur and opacity.
Strong comparison  Strong transient UI uses elevation only where planes overlap.
Repair  Define two elevations: transient and modal. Prefer border or contrast for static grouping.
Equal visual weight
Symptom  Several headings, cards, and CTAs compete.
Strong comparison  Stripe keeps order, form, and final action clearly unequal.
Repair  Name the next decision. Reduce contrast everywhere else before enlarging the primary.
Weak baseline alignment
Symptom  Icons, labels, values, and badges look individually centered but not optically aligned.
Strong comparison  Linear and Superhuman use stable rails across dense rows.
Repair  Overlay guides and align repeated roles; tune icon optical bounds separately.
Cramped whitespace
Symptom  Small gaps occur everywhere, including between unrelated groups.
Strong comparison  Carbon’s scale and the typography-led products use proximity to encode relationships. [34]
Repair  Use 4/8-based tokens and deliberately jump a step between groups.
Inconsistent density
Symptom  A huge header sits above tiny table rows; touch and pointer controls mix arbitrarily.
Strong comparison  VS Code and Maps use density appropriate to input and task.
Repair  Set density by region and platform. Document exceptions.
Generic icon placement
Symptom  Each heading begins with an icon inside a colored rounded square.
Strong comparison  Bear and iA Writer let content headings stand alone; Figma uses icons inside action systems.
Repair  Use icons for recognition or action, not to decorate every noun.
Fake glass
Symptom  Blurred translucent panels reduce contrast over arbitrary backgrounds.
Strong comparison  Maps uses an opaque sheet when readability matters.
Repair  Use transparency only when the underlying context must remain visually active and contrast can be guaranteed.
Unmotivated accent colors
Symptom  Many colors mark categories that do not change behavior.
Strong comparison  Linear uses tiny state colors and otherwise remains neutral.
Repair  Assign every color a named semantic role; delete colors with no behavior or meaning.
Placeholder-only form labels
Symptom  Labels disappear as soon as users type.
Strong comparison  Stripe keeps labels and validation readable.
Repair  Use persistent labels, explicit errors, autofill semantics, and input-specific keyboards.
Decoration-first motion
Symptom  Cards float, bounce, or parallax without clarifying state.
Strong comparison  Things and Live Activities animate insertion, continuity, and status.
Repair  Write the state-change sentence before animating. If no sentence exists, remove the motion.
Happy-path mockup
Symptom  Only the populated desktop state is designed.
Strong comparison  GNOME, Android permissions, Recorder, and Calendar show consequence and progress states.
Repair  Before polish, design empty, loading, error, denial, narrow, keyboard, and recovery states.
Pre-ship anti-vibe audit
• Can the screen be redrawn without most cards?
• Is there exactly one primary action at the current decision?
• Do repeated rows share baselines and rails?
• Are radii, shadows, icon sizes, and spacing drawn from small named sets?
• Does every accent color have a semantic role?
• Are hover, focus, pressed, selected, disabled, loading, error, and success distinguishable?
• Does the mobile layout change structure rather than merely shrink?
• Can keyboard users reach and escape every transient surface?
• Do permissions and destructive actions name the object and consequence?
• Is motion still intelligible and complete under reduced motion?
J  How to use the companion reference index
The companion spreadsheet is the durable lookup layer. Filter Best use category for a quick pattern search, Category tags for mixed queries, Platform for implementation constraints, and Evidence strength or Currentness to exclude weaker or historical material. Source page is the authoritative context; Screenshot or video is the fastest visual entry point. The five analysis columns preserve why the reference is useful and where copying would fail.
Suggested hackathon workflow
• Choose one platform and one density.
• Filter the index to the two or three interaction categories central to the prototype.
• Select one Tier 1 reference for layout, one for interaction, and one for state handling.
• Write down the three lessons being borrowed and the three details intentionally not copied.
• Create the empty, loading, error, and confirmation states before adding decorative polish.
• Run the anti-vibe audit, then tune typography and alignment at final size.

Raycast Root Search
State  Search field plus live-ranked Root Search and Compact Mode.
Platform and use  macOS and Windows • command palette, search
Why it looks and feels good  A near-complete launcher model: focus, ranking, mode, keyboard path, actions, permissions, and escape behavior.
Transferable lesson  Use one query, one selected row, one primary Enter action, and secondary actions behind Command-K.
What not to copy  Do not copy the dark floating shell into a product that cannot deliver fast, well-ranked results.
